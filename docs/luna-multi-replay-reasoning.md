## 怎样交给大模型，而不是再写一套规则

原来的限宽搜索先替玩家选候选，再让模型解释，并不符合本次要求。现在改为：

1. 输入当前本机玩家状态、最近自身状态序列、全部己方野点、已观察清空状态、数值资料和上述**带可信边界的案例**。
2. 大模型自行提出营地顺序、技能/物品施放时机和目标顺序，判断案例是否适用；不预先提供“最近八个点”“每分钟六营”或固定候选路线。
3. 模型可调用 `simulate_route` 核算它自己的提案，并根据失败或收益反馈修改。工具不搜索、更换、重排路线；显式施法计划不触发旧的自动施法策略。
4. 模型通过 `finish_plan` 选择已经核算的方案，给出简短中文决策说明。模型自报金币不进入页面；未建模动作返回 `unsupported`。
5. 返回时从最新玩家位置、血蓝和冷却重新重放；旧局、死亡、关闭、缺失或过期 GSI 使任务取消。保留决策的原始游戏时钟，不将新状态复核冒充一次新模型推理。

保留的程序逻辑是鉴权、格式、生命周期、地图可达性和游戏机制核算，**不是用硬编码条件决定去哪刷**。旧 `planJungleRoute` 只留作显式离线数值基准/回归测试，生产默认不调用，也不作为模型失败回退。

病例资料见 `data/luna-replay-cases.json`。这是检索/提示上下文，**没有训练或更新大模型权重**。

当前规划模型接收的是结构化自身 GSI、最近自身状态和录像观察文本，**不是已接通的实时全屏视觉模型**。上一轮本机 HUD 视觉仍待部署；没有识别到的敌人、队友参与和封野保持未知，不把职业录像中的敌人位置借到用户这局。

## 当前可运行性与配置

最初本机没有 `.env`，因此上一轮只完成了模拟接口验证。用户随后提供外部 Foundry 文件；现已在被忽略的本机 `.env` 中保存 `JUNGLE_PLANNER_MODEL=gpt-6-astra` 和 `JUNGLE_PLANNER_FOUNDRY_ENV_FILE` 引用，未复制密钥，也未改动语音资源。部署与 API 已实际核验。首次实时试跑在两次成功提案响应后达到 25 秒总时限，未完成最终提交；后续离线沙盒实验已完成真实模型对比与选择。

独立配置示例（密钥只放服务端受保护配置）：

```dotenv
JUNGLE_PLANNER_PROVIDER=azure
JUNGLE_PLANNER_MODEL=实际可用的部署名
JUNGLE_PLANNER_FOUNDRY_ENV_FILE=C:/path/to/private-foundry.env
```

外部文件包含 `FOUNDRY_ENDPOINT`、`AOAI_ENDPOINT`、`FOUNDRY_KEY`，仅由服务端读取。也可不用文件引用而直接设置 `JUNGLE_PLANNER_ENDPOINT` 和 `JUNGLE_PLANNER_API_KEY`；两种方式不能混用，以免把文件密钥发送到另一个地址。

也支持 `provider=openai`，实际模型 `gpt-6-astra` 与服务端 `OPENAI_API_KEY`。不要把语音/视觉部署名自动当成规划部署名。官方文档已读取：

- `https://developers.openai.com/api/docs/models/gpt-6-astra`
- `https://developers.openai.com/api/docs/guides/function-calling`

成本/时限边界：每房间最多 30 秒启动一次推理、一次最多 4 轮 Responses、每轮最多 3000 输出 token、8 次工具调用、25 秒超时；一次一个任务，无后台堆积。所有有权控制规划的连接离开后关闭规划，不在无人的房间持续消耗模型请求。

```text
npm run reason:luna
```

配置完成后该命令会发起真实模型请求，对固定合成 Luna 输入输出模型选择及工具估计；无配置时非零退出且不发请求。`report:luna` 是旧离线数值基准，不得拿它冒充真实模型调用。

`replay:gsi` 默认只检查离线自身观测、不发 API 请求；只有显式加 `--numeric-benchmark` 才运行旧数值对照。新网页/桌面端拒绝显示没有规划来源标记的旧服务端路线，防止升级客户端后仍把旧规则结果误认为模型决策。

**这份早期记录的生产原型目标是 180 秒纯野金币；用户后来已明确将沙盒目标扩展为线野总金币。** 战斗/队伍收入仍不能混入。后续引野机制见 v2 文档，环月、野怪技能等仍有缺口；大模型不能凭经验填入假数字来“补完”验证。
