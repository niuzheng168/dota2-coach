# 语音无转录 / 无翻译排查

## 2026-11-12 本地问题复查

现象：文字可翻译并播放，麦克风无转录，点击重新连接后恢复。

旧日志只记录服务启动，没有当时的输入帧或语音引擎状态，因此不能据此认定唯一历史根因。已确认并修复的可复现缺陷：

- 浏览器 WebSocket 的 `open` 只说明连到了本地房间，不说明 Foundry 语音会话已就绪。原实现允许提前开麦，服务端直接忽略没有就绪引擎的音频。
- 初次初始化失败时，文字请求会再次启动引擎，但麦克风帧不会，可能一直没有反馈。
- Voice Live 原来在等待 `session.updated` 超时后仍视为成功，现在超时和提前关闭均明确失败。
- 麦克风复用原来没有确认 AudioContext 已恢复运行，也没有明确的静音输出连接；现在等待恢复、保持静音处理链路、停止开麦时释放设备，并处理异步授权/按住说话取消。

使用同一份 MAI Streaming 配置直接输入已知测试语音能完成识别、翻译与音频输出，不能将当时的现象直接归咎于模型不支持中文。

## 现在的行为

1. 每条客户端连接单独接收 `engine.state`，不再把另一位成员的 ready 状态当成自己的就绪状态。
2. 语音初始化期间禁止开麦；初次启动失败最多自动重试两次，然后明确提示重新连接。
3. 实际收到的音频每秒最多确认一次，说明收到/转发帧数，不返回或保存音频内容。
4. 麦克风下方区分未开麦、没有采集帧、没有音量、服务器未确认和正常接收。
5. ASR 的 `input_audio_transcription.failed` 会显示错误，不再静默忽略。
6. 重连时先停止本地采集，等自己的语音状态就绪后再点击开启；不未经操作自动开启麦克风。
7. 房主保存同传设置更改时，全员收到新配置，旧 WebSocket 和语音会话关闭，然后自动重连。若设置未变化或保存失败，不重置连接；旧会话迟到的音频、字幕和状态不会进入新会话。

## 日志定位

服务输出 `voice.*` JSON 事件，包含时间、连接 ID、房间 ID、角色、引擎状态以及输入/转发帧计数。**不记录录音、字幕文本、密码、Cookie、邀请 token 或 API key。**

| 证据 | 优先检查 |
| --- | --- |
| `startup_failed` / `state=failed` | 服务鉴权、部署名、初始化超时 |
| 收到帧但转发为零 | 语音引擎尚未就绪 |
| `capture_stalled` 且服务端无输入 | 浏览器采集、权限、AudioContext 状态 |
| `input_silent` | 输入设备、硬件静音、是否正在说话 |
| `upload_stalled` | 浏览器至本地服务器的连接 |
| 有转发帧但无 `source_final` | VAD / ASR；查看 `transcription_failed` |
| 断开码 `4001` / `4003` | 会话失效 / 房主撤销权限，不是麦克风独占 |
| 断开码 `4000` | 房主修改同传设置，浏览器自动重连；就绪后需重新开麦 |

本机双账号测试使用不同浏览器配置文件，或普通窗口 + 无痕窗口；同一只麦克风建议轮流给两个角色使用。

## GPT-Live 独立资源

在本地环境设置 `GPT_LIVE_FOUNDRY_ENV_FILE`，只为 GPT-Live 加载另一资源的端点和 key，不替换 Cascaded / Realtime / TTS / 视觉识阵使用的主资源。

外部文件字段为 `FOUNDRY_ENDPOINT`、`AOAI_ENDPOINT`、`FOUNDRY_KEY`。实际部署名通过 `DEPLOYMENT_GPT_LIVE` 配置，也可以放在外部文件中。不要把密钥文件提交到仓库。

部署目录中存在某个条目，不等于 `/openai/v1/live/sessions` 已能创建会话。需要收到 `session.started`，并完成真实音频输入/输出验证；`model_not_deployed` 应作为运行接口故障处理，不能报告 ready。
