# 4K 游戏机上的露娜补刀提醒实测

2026-11-18，提交 `f5aae42`，Dota 2 build 6976。Ryzen 9 7950X3D（32 逻辑处理器）、RTX 5090 D v2、Windows 11 build 26300。游戏客户区 3840×2160；生产代码通过 Windows.Graphics.Capture 采集窗口，GPU 缩到 1920×1080，读取 NV12 兵条。未配对教练端，未调用模型，未自动攻击。

**结论：** 这台机器能跑，但 25 Hz 的识别目标实际跑到约 21 Hz。第一次正补提示的 WPF 绘制明显晚于后续；血条扫描有可复现的大量短命对象分配。两次游戏 FPS 对照的差值方向相反，不宜承诺“无掉帧”，也不能给出固定损失比例。

## 游戏 FPS：同一局试玩，两种顺序

官方 `hero_demo_main`，一级空装露娜，真实自身 GSI，镜头对着自然交战的兵线。使用同一 Release 测试进程，保留 GSI 接收器，按阶段创建或释放生产版 `LastHitPractice`（副本仅加计时点，使用原采集器、识别器及 WPF 提示层；未显示主控制面板）。每段先留 5 秒切换/稳定，再由游戏执行 `cl_resetfps`，25 秒后读 `cl_printfps` 的 **total frames / 25 秒**。

| 相邻且全程有效的配对 | 提醒关 | 提醒开 | 开减关 |
|---|---:|---:|---:|
| 第一轮，先关后开 | 187.8 FPS | 174.2 FPS | −13.6 FPS |
| 第二轮，先开后关 | 173.1 FPS | 179.6 FPS | +6.5 FPS |

两轮各 4 段，顺序分别为关/开/开/关、开/关/关/开；不是相同帧的回放。按约 80–100 ms 轮询检查前台与试玩资格：有 3 段在部分或全部时间不满足条件，保留在 JSON 中但不用于结论。另有第一轮一个完整开启段计入识别统计，其相邻关闭段不符合配对条件。第二轮通过试玩重置回一级，并在该轮临时关闭试玩经验增长。

## 提醒链路：3 个完整开启段，共 75.07 秒

| 指标 | 实测 |
|---|---|
| 有效采样 | 1,567 帧，20.88 Hz；相邻采样间隔中位 46.66 ms，P95 62.42 ms |
| 从开始取帧到得到判断 | 中位 12.78 ms，P95 21.72 ms，最大 34.03 ms |
| 分阶段 P95 | 采集/缩放/回读 5.47 ms；扫描血条 18.69 ms；跟踪与判断 0.005 ms（分位数不可相加） |
| 实际触发 | 664 帧有兵条；9 帧有正补提示；WPF 实际绘制 5 帧。这不是 9 次独立补刀 |
| 从开始取帧到 WPF 完成绘图指令 | 首帧 **551.7 ms**；其余 4 帧分别为 38.3、39.3、39.1、57.5 ms |
| 测量进程开销 | 开启时整机 CPU 的 0.61–0.65%，有效关闭段 0.08–0.09%；开启段采样到的最高工作集约 295 MiB |
| 托管临时分配 | 开启时 1,006–1,008 MiB/s；有效关闭段约 0.3 MiB/s。这是分配速率，不是常驻内存每秒增长 |

首次绘制的计时超过了实现的 180 ms 过期阈值。样本仅有一次冷绘制；计时不包括游戏内掉血到下一次采样，也不代表显示器实际出光。未在这些窗口观察到反补或塔下垫刀提示；没有逐兵的击杀归属标签，不据此估算准确率。项目自带的 19 个补刀专项回归检查全部通过，与自然兵线统计分开。

## 分配来源的独立复核

对相同的预生成 1080p NV12 帧（8 种画面，各 8 根已知兵条）单测 `CreepBars.Read`。预热后正反序测试，原版每帧分配 **45,689,528 字节**，耗时 5.29–5.49 ms；仅在临时副本中把内层去重的捕获式 `result.Any(...)` 换为显式遍历，降为 **368 字节/帧**、0.62–0.65 ms。逐帧识别结果一致。此结果定位了扫描分配热点，**不等于**整套提醒在游戏内能加速同样倍数。建议先消除这处分配、预热首次绘制，再用同一方法复测。

`results.json` 保存全部阶段、样本筛选、延迟分布和微基准结果。`evidence.zip` 内为两轮逐帧计时、GSI 资格/前台计数、整卡 GPU 采样、游戏帧计数摘录及测量用源码，不含游戏画面或 GSI 凭据。

## 追查：为什么算得完，却没达到 25 Hz？

从两个有效 ON1 段取 96 个实测工作耗时（均值 14.73 ms），在同一台机器用等待模拟这 96 次工作，按旧/新/新/旧各跑一遍。不采游戏画面，也不占用游戏窗口。目标均为每 40 ms 采一次：

| 调度方式 | 两次实测频率 | 两次帧间隔 P95 |
|---|---:|---:|
| 练习器现用的相对等待（`TickCount64` + `WaitOne`） | 21.04 / 20.77 Hz | 62.64 / 62.71 ms |
| 以 `Stopwatch` 维持固定时间表，复用视频发送器已有的 `PreciseTimer`，过载不追帧 | 25.00 / 25.00 Hz | 40.25 / 40.22 ms |

不做采集和识别也能重现约 21 Hz，说明调度是刷新不足的重要原因，不是证明游戏已经能稳定跑到 25 Hz。之前的 1080p 试玩记录验证的是功能，并没有同一场景、同一套计时的另一台机器基线。

## 追查：首次提示的 552 ms 花在哪？

对齐同一个采样时间戳：首次提示的判断在 **11.28 ms** 就完成，剩下的 **540.39 ms** 在判断完成至 WPF 绘图结束之间。原实机探针走真实提示层，但没有打开产品主面板，且只记录到一次首次绘制。

另起 3 个新进程，在不显示窗口、不切游戏焦点的条件下，单测透明 WPF 窗口句柄与相同字体的「正补」文字：首次 `EnsureHandle` 用 **152–156 ms**，首次文字构造、测量与绘图用 **17.3–17.5 ms**。另 3 个新进程先准备一个透明窗口及文字，再测试目标窗口和标签，分别用 **16.2–16.6 ms** 和 **0.37–0.53 ms**。这支持提前准备窗口、中文标签，但没有测首次可见 `Show()`、4K 合成或出光，不能把 540 ms 全归咎于字体或窗口创建。完整客户端应从点击练习到首个真实提示再做冷启动对照。

`timing-diagnostics.zip` 含上述两个独立测试的源码、方法和原始数字。仅追加诊断，未改产品代码。
